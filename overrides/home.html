muster connects the MCP servers an organisation runs — a factory's MES and maintenance system, a service desk and its directory, a CRM and an ERP, a platform's Kubernetes and Prometheus, your own — and serves their tools through a single authenticated endpoint. Agents connect once, find tools without flooding their context window, run procedures as deterministic workflows, and make every call as the person they work for.

Where it fits shop floor · service desk · back office · platform

The systems differ. The shape of the work does not.

A shift lead, a service-desk analyst, an account manager and an engineer on call ask their agents very different questions, and every answer lives in three or four systems that were never built to be read together. Each system speaks MCP through its own server; muster is where the servers meet. One example per area: the servers behind the endpoint, the procedure sewn into a workflow, and the identity every call carries.

Manufacturing workflow_line-stop-triage

“Line 3 stopped at 06:40. Why, and what did it hit?”

The MES has the downtime event, the SCADA historian the alarms around it, the ERP the production order that was running, the maintenance system the asset's history. The workflow reads the four in order and opens a work order only when the alarm matches a known failure mode.

Workflow engine kind: Workflow · muster.giantswarm.io/v1alpha1

Procedures become tools.

Work in any of these systems is a sequence: find the record, read what hangs off it, ask a second system, compare, decide. Left to an agent, the sequence is rediscovered on every run, differently each time, at full token cost. A workflow sews the sequence into one tool. It is a list of steps — tool calls, forEach loops and parallel groups — gated by conditions and joined by templates. muster exposes it as workflow_<name> with the arguments you declared; the steps run the same way every time, and every run leaves a durable execution record. Below, the platform example in full; a line stop or a renewal brief is written with the same constructs.

workflow.yamlkubectl apply -f · or core_workflow_create
apiVersion: muster.giantswarm.io/v1alpha1
kind: Workflow
metadata:
  name: pod-triage
  namespace: muster
spec:
  description: Find the pods of a workload that are not running and gather their evidence
  args:
    namespace: { type: string, required: true }
    selector:  { type: string, required: true }
  steps:
    - id: pods
      tool: x_kubernetes_list
      args: { kind: Pod, namespace: "{{ '{{' }} .input.namespace {{ '}}' }}", labelSelector: "{{ '{{' }} .input.selector {{ '}}' }}" }
    - id: events
      tool: x_kubernetes_list
      args: { kind: Event, namespace: "{{ '{{' }} .input.namespace {{ '}}' }}" }
      condition:
        template: "{{ '{{' }} gt (len .results.pods.items) 0 {{ '}}' }}"
    - id: logs
      forEach:
        items: "{{ '{{' }} .results.pods.items {{ '}}' }}"
        as: pod
        steps:
          - id: tail
            tool: x_kubernetes_logs
            args: { name: "{{ '{{' }} .vars.pod.metadata.name {{ '}}' }}", namespace: "{{ '{{' }} .input.namespace {{ '}}' }}", tailLines: 50 }
            allowFailure: true
    - id: signals
      parallel:
        - id: restarts
          tool: x_prometheus_query
          args: { query: 'increase(kube_pod_container_status_restarts_total{namespace="{{ '{{' }} .input.namespace {{ '}}' }}"}[1h])' }
        - id: alerts
          tool: x_prometheus_alerts
          args: { namespace: "{{ '{{' }} .input.namespace {{ '}}' }}" }
  onFailure:
    - id: note
      tool: x_slack_post
      args: { channel: "#oncall", text: "pod-triage failed for {{ '{{' }} .input.namespace {{ '}}' }}/{{ '{{' }} .input.selector {{ '}}' }}" }
  output:
    pods:     "{{ '{{' }} .results.pods.items {{ '}}' }}"
    restarts: "{{ '{{' }} .results.restarts.data.result {{ '}}' }}"
    alerts:   "{{ '{{' }} len .results.alerts.alerts {{ '}}' }}"

  • Templates

    Step arguments are Go templates with sprig, over .input, .results and .vars. Every step's result is referenceable by every later step; a reference to an undefined key fails the step instead of passing an empty string on.

  • Conditions

    A step is gated by a boolean template, by a tool call checked against expect, or by an earlier step's result. Malformed conditions are rejected at kubectl apply time by CEL and by core_workflow_validate.

  • forEach and parallel

    Fan out over clusters, namespaces or pods with forEach, each iteration addressable afterwards; run independent steps concurrently with parallel and pick their results up after the group.

  • Failure handling

    allowFailure records a failure and continues, the error available to later conditions. When a step fails for real, the workflow's onFailure handlers run as best-effort rollback.

  • Shaped output

    An output template returns a small, structured document instead of every step's payload. JSON types are preserved: len stays a number, an array stays an array, a version string stays "1.20".

  • A durable record

    Every run is a WorkflowExecution with per-step status, inputs, results and timing, listed with core_workflow_execution_list, and an OpenTelemetry trace with one span per workflow and per step.

Workflows compose: one workflow calls another's workflow_<name> tool, a toolset selects them with workflow:<name>, and an agent finds them by intent through filter_tools. Create workflows · Workflow reference

Servers and workflows are resources.

On a cluster, muster runs in Kubernetes mode: MCPServer, Workflow and WorkflowExecution are custom resources reconciled by muster itself. Status, conditions and events say which servers are reachable now and which workflows have every tool they need. A server is registered in a pull request, reviewed like any other manifest and rolled out by Flux; the people who use it configure nothing.

MCPServerkubectl get mcpservers
spec:
  type: streamable-http
  url: https://mcp-kubernetes.muster.svc/mcp
  toolPrefix: k8s
  auth:
    type: oauth
    forwardToken: true
    requiredAudiences: [dex-k8s-authenticator]
status:
  state: Running
  conditions: [Connected, ToolsDiscovered]

Connected, health-checked and reconnected with backoff. The tool list is followed as it changes; the status and the events tell the story.

What the chart ships

  • The three CRDs, and a separate muster-crds chart when their lifecycle should be its own release
  • RBAC, with editor roles for MCPServer and Workflow so teams register their own servers
  • NetworkPolicy and a Cilium variant restricting ingress to the aggregator and metrics ports
  • ServiceMonitor, a PrometheusRule set and a Grafana dashboard
  • Ingress, or Gateway API HTTPRoute and BackendTrafficPolicy
  • HPA and PDB, and Valkey-backed sessions and grants for more than one replica
  • An extra CA bundle for MCP servers behind a private CA

Identity and single sign-on OAuth 2.1 · RFC 9728 · RFC 8693 · PKCE

Every call is made as the person.

A shared muster is an OAuth 2.1 resource server in front of Dex. A person logs in once and gets one session; muster carries that identity to every MCP server behind it and records who called what. Nothing muster adds widens access: a toolset bounds what the model can see, and the backends' own authorization stays the boundary.

$ muster auth status

muster: authenticated
  Endpoint: https://muster.example.com
  Identity: dana@example.com
  Expires:  in 29 minutes · session 30 days

MCP Servers:
  mcp-kubernetes    Connected  [SSO: Forwarded]
  mes               Connected  [SSO: Forwarded]
  erp               Connected  [SSO: Exchanged]
  salesforce        Not authenticated   Run: muster auth login --server salesforce

  • One login, one session

    The CLI, the IDE bridge and any client that implements the MCP authorization flow log in through the browser at Dex. Tokens live on disk with mode 0600, never in logs. Access tokens last 30 minutes and are capped to the provider's; the refresh token rolls for 30 days, aligned with Dex.

  • Identity travels downstream

    Servers that trust the same Dex — in-house ones in front of an MES, a directory or a cluster — receive the person's ID token with the audiences they require. Servers behind another IdP get an RFC 8693 token exchange there. A vendor's server with its own OAuth gets a browser login once per person, and AWS-hosted servers a SigV4 signature.

  • Hardened by default

    PKCE on every flow, state validation, AES-256-GCM encryption of stored tokens, rate limits on the registration, authorization and token endpoints, SSRF and DNS-rebinding guards on client metadata and redirect URIs.

  • Standard endpoints

    Protected-resource metadata under /.well-known (RFC 9728), client ID metadata documents, dynamic client registration where the deployment allows it. Any MCP client that speaks the authorization spec connects without a bridge.

  • Toolsets, per request

    X-muster-Toolset: preset:read-only, workflow:pod-triage declares the tools a request may see and call. Built-in and operator-defined presets, selectors by server, workflow, tool or label. Evaluated on every request; a toolset never widens the catalogue.

  • Who called what

    Every tool call carries the person's identity into OpenTelemetry traces, Prometheus metrics and structured logs. Sessions, grants and OAuth state move to Valkey for more than one replica, and muster waits for it rather than splitting sessions.

Discovery 13 meta-tools · x_<server>_<tool>

A catalogue that fits a context window.

An MCP client loads every tool definition of every attached server before the first question is asked; an organisation's servers contribute hundreds. muster's clients see thirteen meta-tools instead. filter_tools ranks the catalogue against a query and returns a short, summarised page; describe_tool returns one schema; call_tool runs it. The catalogue can be hundreds of tools wide and still cost a few hundred tokens a turn. Servers that serve the same tools for different targets form a family and appear as one surface with an instance argument.

Get started brew · curl · helm · go

Ten minutes to an IDE calling tools through muster.

muster is a single static binary for Linux, macOS and Windows, a container image and a Helm chart. Binaries are signed in CI and verified by muster self-update.

brew trust giantswarm/muster
brew install giantswarm/muster/muster
os="$(uname -s | tr '[:upper:]' '[:lower:]')"
arch="$(uname -m | sed 's/x86_64/amd64/; s/aarch64/arm64/')"
curl -fsSL -o muster "https://github.com/giantswarm/muster/releases/latest/download/muster-${os}-${arch}"
chmod +x muster && sudo mv muster /usr/local/bin/
helm repo add giantswarm https://giantswarm.github.io/giantswarm-catalog/
helm install muster giantswarm/muster --namespace muster --create-namespace
go install github.com/giantswarm/muster/v5@latest
